# StudyRoom Flyway 基线与恢复手册

## 目的与当前授权边界

本手册定义如何让已有的 StudyRoom v1 数据库安全进入 Flyway 管理。阶段 11 只交付迁移代码、自动化验证和操作手册；不得连接、baseline 或迁移生产数据库。生产执行属于阶段 12，必须重新取得明确确认。

Flyway 配置固定为：

- `baseline-on-migrate: false`：拒绝自动接管任何非空未知数据库。
- `validate-on-migrate: true`：启动前校验已登记迁移的校验和。
- `clean-disabled: true`：应用运行时禁止清库。

## 数据库分类

| 状态 | 处理方式 |
| --- | --- |
| 全新空库 | 直接启动后端，自动执行 V1 及后续迁移。 |
| 非空且没有 `flyway_schema_history` | 后端必须拒绝启动；完成本手册的盘点和隔离演练后才能显式 baseline。 |
| 已有 Flyway 历史 | 先运行 `validate`；校验和不一致时停止，不修改历史迁移。 |
| 结构来源不明或与 V1 不一致 | 停止迁移，先生成差异报告并编写新的兼容迁移，不能强行 baseline。 |

## 阶段 12 前置证据

执行者需要在变更单中记录：

1. 精确数据库实例、库名、MySQL 版本和字符集。
2. 表、列、索引、外键和约束的只读结构清单。
3. 行数与关键业务对象计数，不导出密码哈希、会话或用户内容到仓库。
4. 一份一致性备份和上传目录备份的 SHA-256、大小、时间和保存位置。
5. 在隔离 MySQL 8 实例中完成至少两次“恢复备份 → 比对 V1 → baseline V1 → migrate V2 → 应用冒烟 → 恢复演练”。
6. 停机窗口、负责人、回滚判定条件和预计恢复时间。

## 显式 baseline 原则

只有当隔离副本证明现有结构与 `V1__studyroom_v2_baseline.sql` 的逻辑结构一致时，才可将该库登记为版本 `1`。baseline 只登记历史，不会替用户修复结构差异。

生产操作必须使用一次性受限凭据和受控发布工具，不在命令历史、脚本参数、日志或截图中暴露密码。执行流程为：

1. 阻止新的云端写请求并等待在途事务结束。
2. 再做一次数据库和上传目录备份，复验 SHA-256。
3. 以只读方式重新获取结构与计数，确认与演练输入一致。
4. 使用 Flyway 显式登记 baseline 版本 `1`。
5. 立即执行 `validate`，随后执行 `migrate`，只允许预先审批的后续版本。
6. 验证 `flyway_schema_history`、新列/表、外键、管理员登录、普通读取和最小写入回滚用例。
7. 解除写入前保存迁移日志、结构清单和业务计数。

本仓库不提供可以直接粘贴到生产环境的含密钥命令。阶段 12 发布工具必须从受保护环境注入连接信息，并在日志中脱敏。

## 失败与恢复

出现以下任一情况立即停止并维持写入关闭：

- 备份校验和或业务计数不一致。
- V1 结构差异未解释。
- Flyway 校验失败、迁移失败或历史校验和改变。
- 管理员认证、会话、核心读取或写入冒烟失败。
- MySQL 磁盘、内存、锁等待或错误日志超过阶段 12 门限。

恢复顺序：

1. 保存失败现场的迁移日志、`flyway_schema_history` 和只读结构快照。
2. 不编辑或删除已经发布的迁移文件，不手工伪造成功记录。
3. 若迁移事务已完整回滚，修复原因后从新的隔离副本重新演练。
4. 若存在部分 DDL，重建空数据库并从已校验备份恢复；不要在原库上猜测性逆向修改。
5. 恢复后复核备份 SHA-256、业务计数和应用冒烟，再决定继续旧版服务或安排新的修复窗口。

备份至少保留 30 天；销毁备份仍需后续明确决定。
